# Ручное обогащение вакансии через Supabase Studio

Инструкция для того, кто вручную заполняет поля вакансии в Studio после того,
как работодатель ответил на письмо (`/employers/sv`, `/employers/nb`) или
когда факты честно переносятся из текста исходного объявления. Написана
16.08.2026 вместе с реализацией живого героя на главной (см. CLAUDE.md,
раздел «Герой на главной») — по мере обогащения вакансий эти строки должны
перестать пустовать и герой начнёт показывать их вместо fallback-текста.

## Правило №1 — источник факта определяет `verification_level`

**Перенос факта из текста исходного объявления НЕ поднимает
`verification_level` выше `SOURCE_CONFIRMED`.** Сколько бы полей ни было
заполнено — хоть все пять — уровень остаётся тем же, что проставил импортёр.

`EMPLOYER_CONFIRMED` — это отдельная, более сильная заявка о статусе:
согласно `dict.verification.meaningEmployerConfirmed` («Работодатель найден
в реестре, ставка и условия сверены») и `checkedEmployerConfirmed` («Реестр
компании + коллективный договор + жильё/дорога не скрыты»). Поднимать
уровень можно только когда это реально сделано:

- работодатель ответил на письмо и подтвердил условия напрямую, **или**
- редакция сверила работодателя по реестру (Bolagsverket/Brønnøysund).

Если просто переписать цифру из шведского текста в поле БД и заодно
поднять `verification_level` — бейдж на карточке будет врать ровно в том
смысле, за который платформа критикует посредников, только на уровень
абстракции выше: поля честные, бейдж — нет.

**Только то, что реально написано.** Не достраивать логикой «обычно у таких
работодателей бывает X». Если в объявлении зарплата не названа —
`wage_amount` остаётся `null`, а не средней по рынку цифрой. Если
формулировка «boende kan ordnas» — «жильё можно устроить» — не значит
`included` (это конкретно «жильё оплачено»). С 17.08.2026 для такого
подтверждённого факта есть честное значение `available`: жильё доступно, но
стоимость и удержание из зарплаты не указаны.

**Ловушки, на которые стоит обратить внимание при чтении шведского текста**
(пойманы вживую 16.08.2026 при проверке 69+225 реальных объявлений):

- `boende` в контексте ухода за пожилыми почти всегда значит «дом
  престарелых / место проживания подопечных» («särskilt boende»,
  «gruppboende»), а не жильё для работника. Читать контекст вокруг слова,
  не просто искать его вхождение.
- `logi` (жильё) — не путать с частью слова `logistik`.
- Число с «kr» рядом необязательно зарплата — часто это годовой лимит на
  фитнес-компенсацию или похожий бонус («5000 kr/år» на тренировки).
- `resa` — не всегда про переезд/дорогу: «vår resa mot att bli Sveriges
  bästa äldreomsorg» — это метафора о развитии компании, не о поездке.
- Явно названный коллективный договор («PAN 25», «HÖK») — редкость (18.6% на
  реальной выборке 16.08.2026). Обычно просто «Lön enligt kollektivavtal» —
  это **не повод заполнять `collective_agreement`** сам по себе, см. Правило
  №3: с 16.08.2026 схема различает «назван» и «есть, без названия» отдельным
  полем `agreement_status`, и текстовое поле можно заполнять только когда
  название реально известно.

## Правило №2 — какую вакансию вообще брать

Не каждое шведское объявление годится. По результатам сканирования 16.08.2026
(см. CLAUDE.md, разделы «Категории импорта» и «Решение реализовано»): в
сегменте домашнего ухода/уборки/логистики коммун честно переносимых фактов
почти нет — эти объявления написаны для местных шведов, не для переезжающего
работника, поэтому там просто не поднимается тема жилья и дороги. Заметно
богаче — сегмент стройки/монтажа/спецтехники, особенно объявления от
кадровых агентств («…Bemanning AB», «…byggbemanning och rekrytering AB»): у
них жильё, суточные (`traktamente`) и ссылка на коллективный договор
встречаются кратно чаще, потому что бизнес этих агентств буквально в том,
чтобы возить людей на объект. С того же дня импортёр сам целится в этот
сегмент (`OCCUPATIONS` с `regionRestricted` + ось по работодателю в
`src/lib/contractors.ts`, приоритет — Norrbotten/Västerbotten) — обогащать
вручную стоит начинать именно с вакансий оттуда, шанс найти честные факты
там выше по построению, не только по статистике из проверки.

Хороший практический тест перед тем, как открывать Studio: прочитать текст
объявления на `source_url` вакансии и проверить, есть ли там **прямо
написанное** упоминание хотя бы 2 из 5 полей. Если работодатель — кадровое
агентство, а не сама компания-заказчик, шанс выше.

## Правило №3 — колонки, формат, значения

Таблица `public.vacancies`. Найти строку по `title` / `employer_name` /
`external_id` (номер объявления, виден в конце `source_url`).

**`agreement_status` и `collective_agreement` — только через SQL Editor одним
`UPDATE`. Table Editor для этих двух полей не использовать вообще**, не как
запасной вариант с оговоркой. Инлайн-редактирование ячейки в Table Editor
сохраняет **каждую клетку отдельным UPDATE** сразу по Enter/потере
фокуса — способа отредактировать обе колонки одним запросом через эту форму
интерфейса физически нет, значит совет «сначала одно поле, потом другое»
всё равно сведётся к двум раздельным запросам, один из которых упадёт на
CHECK `vacancies_agreement_name_ck` в зависимости от того, в каком порядке
вы кликнули по ячейкам (а `collective_agreement` физически стоит раньше
`agreement_status` в списке столбцов — при обычном просмотре слева направо
это ровно падающий порядок). Полагаться на «не перепутать порядок клика»
— не инструкция, а лотерея. Остальные поля (`wage_amount`,
`housing_status` и т.п.) таким ограничением не связаны, их через Table
Editor редактировать можно как обычно.

Пример корректного запроса — обе колонки в одном `UPDATE`:

```sql
update public.vacancies
set agreement_status = 'named',
    collective_agreement = 'Byggnads',
    housing_status = 'included',
    hours_per_week = 40
where external_id = '31356468';
```

Проверено вживую 16.08.2026 (и повторно тем же днём свежим запросом): один
комбинированный `UPDATE` проходит без ошибок. Двумя раздельными
`UPDATE` тоже можно — CHECK смотрит на состояние строки на момент каждого
конкретного запроса, не на историю: `agreement_status = 'named'` первым
запросом, затем `collective_agreement` вторым — проходит; обратный
порядок — падает с `23514`. Именно поэтому Table Editor и не годится:
там нет контроля, в каком порядке вы кликнете по ячейкам, а
`collective_agreement` физически стоит раньше `agreement_status` в списке
столбцов — угадать правильный порядок из самого интерфейса неоткуда. Один
`UPDATE` с обеими колонками сразу снимает вопрос порядка полностью, поэтому
и остаётся единственной рекомендацией, а не просто более простой.

| Колонка | Формат | Важно |
|---|---|---|
| `wage_amount` | число, `numeric` | без пробелов и разделителей тысяч |
| `wage_currency` | `'SEK'` \| `'NOK'` \| `'EUR'` | ровно эти строки, регистр важен |
| `wage_type` | `'net_hour'` \| `'gross_hour'` \| `'gross_month'` | ровно один из трёх — другое значение молча не покажет подпись единицы (`WAGE_UNIT_KEY` в `VacancyCard.tsx` не найдёт ключ), но и не упадёт с ошибкой |
| `housing_status` | `'included'` \| `'deducted'` \| `'available'` \| `'unknown'` | `available` — жильё для работника реально есть/может быть организовано, но цена и удержание из зарплаты не названы. Не заменять им `included`: «boende kan ordnas» не означает, что жильё оплачено. Опечатка тихо трактуется как `unknown` (см. `toHousingStatus()` в `vacancies.ts`). |
| `travel_status` | `'included'` \| `'deducted'` \| `'unknown'` | то же |
| `hours_per_week` | целое число | из `scope_of_work.max` объявления, если там честные 100% (не диапазон вроде `min:0, max:100` — это признак расплывчатого/гибкого графика, не берите как факт) |
| `agreement_status` | `'named'` \| `'exists_unnamed'` \| `'unknown'` | заполнять в одном `UPDATE` вместе с `collective_agreement`, не по отдельности — см. правило выше |
| `collective_agreement` | свободный текст, только при `agreement_status = 'named'` | точное название («Byggnads», «PAN 25») — не общая формулировка. БД физически не даст сохранить это поле при любом другом `agreement_status` (CHECK `vacancies_agreement_name_ck`) — ошибка constraint при сохранении значит именно это: обе колонки нужно поставить одним запросом, см. правило выше |
| `verification_level` | **не трогать** | остаётся тем, что проставил импортёр (обычно `SOURCE_CONFIRMED`) — см. Правило №1 |

**`agreement_status` — как выбирать значение:**
- В объявлении написано «Lön enligt kollektivavtal» / «Vi erbjuder
  kollektivavtal» без названия → `agreement_status = 'exists_unnamed'`,
  `collective_agreement` оставить `null`. Это реальная информация (минимум
  чем-то гарантирован) и засчитывается в порог героя наравне с `'named'` —
  но конкретную ставку по нему показать нельзя, карточка сама не покажет.
- В объявлении явно назван договор («Byggnads», «PAN 25», «HÖK») →
  `agreement_status = 'named'`, `collective_agreement` = точное название.
- Про договор вообще ничего не сказано → `agreement_status = 'unknown'`
  (значение по умолчанию, отдельно ставить не нужно).

`updated_at` трогать не нужно — на таблице есть триггер `vacancies_updated_at`
(`before update`, ставит `now()`), любое изменение через Studio (SQL Editor
или инлайн-редактирование ячейки) обновляет его само. Значит попадание в
окно 40 самых свежих для героя на главной (`HERO_CANDIDATE_WINDOW` в
`src/lib/vacancies.ts`) происходит автоматически, отдельно ничего поднимать
не нужно.

## Проверить после

- Порог для героя на главной — `HERO_MIN_FILLED_FIELDS = 3` в
  `src/lib/vacancies.ts`: заполненными считаются `wage_amount`,
  `housing_status`/`travel_status` (только не `'unknown'`), `hours_per_week`,
  `agreement_status` (`'named'` ИЛИ `'exists_unnamed'` — оба варианта,
  только не `'unknown'`). Три из пяти — вакансия становится кандидатом.
- Если `agreement_status = 'named'`, но на карточке нет цифры тарифа рядом
  с § — это не баг: цифра появляется только если ещё и заведена ставка в
  `collective_agreements`/`collective_agreement_rates` (отдельная таблица,
  сейчас там только PAN 25). Название договора и его тарифная ставка —
  разные вещи, первое можно знать без второго.
- На карточке (что в `/#jobs`, что в героя — компонент один и тот же)
  незаполненные поля показываются честно («нужно уточнить»), не исчезают.
  Если что-то исчезло — значит поле осталось `null`/`unknown`, а не баг
  отображения.
