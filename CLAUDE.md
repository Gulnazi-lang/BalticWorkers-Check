# BalticWorkers Check

Платформа проверенных вакансий за границей для работников из Балтии (сейчас — Швеция и Норвегия).
Статус: MVP-витрина на Supabase, задеплоена на Vercel, кастомный домен ещё не заведён.

**Переименование 14.08.2026: NordicWork Check → BalticWorkers Check.** Причина — «Nordic» жёстко
привязывал бренд к направлению (Скандинавия), хотя ценность продукта — в честной проверке вакансий
для аудитории (работников из Балтии), а направления могут расшириться (обсуждалась Германия — там
у гос. API реально есть числовая зарплата примерно в 32% вакансий против ~2% у шведского JobTech,
проверено напрямую через API 14.08.2026, а не на глаз). «Check» сохранён — это уже устоявшийся
смысл проверки. Домен выбран `.com` (`balticworkers.com`), не `.lv` — национальный TLD одной
страны повторил бы ту же ошибку сужения бренда, которую и чинили. Код переименован полностью;
**руками ещё нужно**: переименовать репозиторий на GitHub, название проекта в Supabase
(косметическое), купить домен.

Vercel-проект переименован в `baltic-workers-check` 14.08.2026 — но переименование не переносит
домен автоматически, только у следующего деплоя. Фолбэк-URL в `siteUrl()`
(`src/app/actions/alerts.ts`, `src/app/api/notify/route.ts`) обновлён на новый адрес тем же
коммитом, который и вызвал этот новый деплой. Если снова понадобится сменить домен — учитывать
эту задержку и лучше сразу задавать `NEXT_PUBLIC_SITE_URL` в Vercel Environment Variables, тогда
фолбэк в коде вообще не участвует.

## Совместная работа Claude и Codex (договорённость 14.08.2026)
Проект ведут параллельно два ассистента — этот файл общий контракт между ними, а не заметки
одного из них:
- Перед изменениями — проверить `git status`, не перезаписывать чужие незакоммиченные правки.
- Одна задача — один небольшой законченный коммит (например «карточка вакансии», «импортёр»),
  не смешивать несвязанные изменения.
- После работы, если менялась структура, схема БД или важное решение — обновить этот файл.
- Секреты, `.env.local`, ключи Supabase/Vercel — никогда в чат, никогда в git.
- Перед тем как оставить задачу другому: `npm run lint` (и по возможности `npm run build`) без
  ошибок, короткое резюме — что сделано, что нет, какие файлы менялись.
- Известный остаточный риск: два ассистента могут независимо решить одну и ту же проблему
  по-разному в один день — при находке дублирующей/конфликтующей работы решать через этот файл,

## Страницы работодателей `/employers/sv` и `/employers/nb`
Появились 16.08.2026 как условие для рассылки шведским коммунам и норвежским подрядчикам: ссылка
в подписи письма должна вести на текст на языке адресата. До этого она вела на главную для
соискателей, где сотрудник коммуны видел интерфейс на английском и вакансии, которые ему не нужны.

**Это не локали сайта, и смешивать их с `LOCALES` нельзя.** Разная аудитория (работодатель, а не
соискатель), разный текст, витрина на sv/nb не переводится и переводиться не должна. Отсюда всё
остальное устройство:
- Свой мини-конфиг `src/i18n/employers/config.ts` (`EMPLOYER_LANGS`), не `@/i18n/config`.
- Свой словарь `src/i18n/employers/{sv,nb}.json` — 40 ключей, форма файлов совпадает 1:1.
  Ключи из `src/i18n/messages/*.json` сюда не тянуть: там поиск вакансий и подписка, здесь —
  уточнение условий, пересечение почти нулевое.
- Свой корневой layout `src/app/employers/[lang]/layout.tsx` с `<html lang>`. В проекте нет
  `app/layout.tsx`, поэтому html/body задаёт верхний layout каждой ветки — как и `[locale]/layout.tsx`.
- **`employers` исключён из matcher'а в `src/proxy.ts`.** Без этого cookie `NEXT_LOCALE` или
  `Accept-Language` увели бы ссылку из письма в `/lv/employers/sv`. Проверено curl'ом: с
  `NEXT_LOCALE=lv` и `Accept-Language: lv` страница отдаёт 200 без редиректа.
- В `sitemap.ts` они отдельной функцией `employerPages()` с альтернативами только друг на друга —
  пять локалей витрины сюда не подмешивать.
- `dynamicParams = false`: `/employers/de` и `/employers` дают честный 404, а не пустую страницу.

**Код норвежского — `nb` (bokmål), не `no`.** `no` это макроязык; страница написана на букмоле.

**Тон страниц — не продажа размещения.** Формулировка: «ваша вакансия публичная, мы её уже
показываем, помогите передать условия точно». Прямым текстом: не продаём место, ответ ни к чему
не обязывает, статус проверки не продаётся. Это продолжение «Ядра бренда», а не маркетинг.

Мелочь локализации, которую легко потерять при правках: шведский использует кавычки `”...”`,
норвежский — `«...»`. В `sv.json` ёлочек быть не должно.

**Контактные адреса** (`baltworkers@gmail.com`, второй в копии `gelvua@gmail.com`) захардкожены
константами в `src/app/employers/[lang]/page.tsx`. На `/for-employers` до сих пор стоит заглушка
`hello@balticworkers-check.example` — несуществующий домен; её отдельно не трогали.

**Обещание «не хотите показываться — уберём вакансию» закрыто механизмом** (16.08.2026,
таблица `excluded_vacancies`, миграция `014`) — см. раздел «Снятие вакансии по просьбе
работодателя» ниже.

## Снятие вакансии по просьбе работодателя (`excluded_vacancies`, 16.08.2026)
Механизм под обещание со страниц `/employers/sv` и `/employers/nb`. До него импортёр возвращал
снятую вакансию при следующем прогоне, то есть обещание держалось только на том, что никто не
запустит импорт.

- `supabase/014_excluded_vacancies.sql` — таблица. Ключ `(source_name, external_id)`, **те же
  колонки, что в `vacancies`**, а не отдельный словарь `'jobtech'/'nav'`: в `source_name` лежат
  `Arbetsförmedlingen` и `NAV`, второй набор имён источников пришлось бы маппить.
- `src/lib/importers/exclusions.ts` — `loadExclusions` / `isExcluded` / `purgeExcluded`,
  общий хелпер для обоих импортёров.
- Подключено в `/api/import` и `/api/import-nav`: отсев из свежей выдачи **и** `purgeExcluded`,
  который убирает то, что попало в базу до обращения. Оба роута возвращают `purged` в ответе.
- Имена источников вынесены в `JOBTECH_SOURCE_NAME` / `NAV_SOURCE_NAME` — по ним же ищется
  exclusion-лист, и расхождение строк тихо отключило бы фильтр.

**Два уровня исключения, и второй не избыточен.** Проверено на живом API 16.08.2026: id
объявления НЕ переиспользуется (у JobTech глобальный возрастающий счётчик — за полгода
30 646 364 → 31 356 660, корреляция с датой публикации 0.97, дублей нет; у NAV uuid). Значит
исключение по id безопасно — но повторная публикация той же вакансии получает НОВЫЙ id и мимо
такого исключения проходит.

**Какой уровень выбрать при вставке записи в Studio — не наугад:**
- **По умолчанию `external_id`** — снимает одно конкретное объявление. Подавляющее большинство
  обращений будет об одной ставке, не обо всём работодателе.
- **`employer_name` — только когда работодатель прямо просит убрать себя целиком**, а не одну
  вакансию. Уровень асимметричный: у `external_id` риска нет (снимается ровно то объявление, о
  котором просили), а `employer_name` снимает ВСЕ его вакансии в источнике, включая те, про
  которые не спрашивали, — это тоже не то, что мы обещали, только в другую сторону.
- **В `reason` — дословно, что именно просили.** Не пересказ своими словами: если позже
  окажется, что уровень выбран не тот (например, при обращении про одну ставку записали
  `employer_name`), только дословная цитата покажет, ошибка это ввода или работодатель
  действительно просил убрать себя целиком.

Сравнение регистронезависимое (`trim().toLowerCase()` и при загрузке, и при сопоставлении,
`src/lib/importers/exclusions.ts`), спецсимволы `ilike` экранируются. Уникальный индекс на
`employer_name` — `lower(btrim(...))`, не просто `lower(...)`: иначе `"Bodens kommun"` и
`"Bodens kommun "` (хвостовой пробел при вставке в Studio) не считались бы дублем на уровне БД,
хотя в рантайме матчатся как один и тот же работодатель.

**Известное ограничение сопоставления по имени (не решать сейчас, просто держать в голове):**
`employer_name` ловит точное совпадение имени в фиде, а не все связанные юрлица. `"Bodens
kommun"` и `"Bodens kommun, Socialförvaltningen"` — разные строки, исключение по первой не
затронет вторую. Разные написания одной компании (лишний суффикс, `AB`/`Ab`) тоже не совпадут.
JobTech отдаёт `employer.organization_number` (проверено, приходит), NAV — свой идентификатор;
сейчас ни то, ни другое не сохраняется в `vacancies`. Если обращений станет заметно больше —
правильный ход колонка с орг-номером и исключение по нему, а не по имени.

**Заполняется руками через Supabase Studio** — обращения приходят письмами на
`baltworkers@gmail.com`. Формы на сайте нет и не нужна, пока поток не вырастет.

**ВАЖНО про порядок выката: сначала миграция, потом деплой кода.** `loadExclusions` сознательно
НЕ глотает ошибку запроса — пустой список означал бы «никто не исключён», и импорт вернул бы на
сайт вакансию работодателя, которому мы обещали её убрать. Побочный эффект: пока таблицы нет,
импорт падает целиком, включая ежедневный cron `/api/import` в 05:15. Это осознанный размен —
упавший импорт заметен, тихо нарушенное обещание нет.

**«Заметен» держится только если реально попадает в лог, а не просто в код ответа.** Оба роута
и раньше возвращали 5xx при любой ошибке (не 200 — Vercel Cron не засчитал бы такой прогон
успешным), но Vercel Runtime Logs по умолчанию пишут код статуса и время выполнения, НЕ тело
JSON-ответа. Без явного `console.error` сообщение об ошибке нигде не появлялось бы, кроме как в
самом HTTP-ответе, который никто не читает у cron-запуска. Добавлено 16.08.2026: `console.error`
в каждой точке возврата ошибки в `/api/import` и `/api/import-nav`, с префиксом `[import:jobtech]`
/ `[import:nav]`. Различить причину падения можно по тексту, а не только по факту падения —
префиксы у разных источников ошибки не пересекаются: `excluded_vacancies (...)` и
`purge by external_id`/`purge by employer_name` (сбой самой таблицы исключений,
`src/lib/importers/exclusions.ts`) отдельно от `JobTech (term): ...` и `NAV feed (...)`/
`NAV feedentry ...` (сбой фида) отдельно от `vacancies upsert failed`/`deactivate failed`
(сбой записи в БД).

## Герой на главной — живая вакансия, не демо (16.08.2026)
Прежняя хардкод демо-карточка в первом экране главной (`dict.home.demo.*`, монтажник в Boden, все
поля заполнены) убрана. Проблема была двойная: реальный пользователь целевой аудитории (монтажник,
работает в Бодене) на ней спотыкался — не понимал, вакансия это или пример; и она противоречила
подзаголовку («честно показываем, что подтверждено, а что нет») — сама демо-карточка была
идеальным случаем, каких в реальных данных не бывает.

- `getHeroVacancy()` в `src/lib/vacancies.ts` — отдельная функция, не переиспользует уже
  отфильтрованный `vacancies` из `getVacancies()`: герой не должен зависеть от текущего поиска
  пользователя (`?occupation=&country=`).
- Правило отбора: среди `HERO_CANDIDATE_WINDOW` (40) самых свежих published-вакансий (```is_demo
  = false```) берём те, где заполнено минимум `HERO_MIN_FILLED_FIELDS` (3) из пяти ключевых полей
  (`wageAmount`, `housingStatus`/`travelStatus` — только не `unknown`, `hoursPerWeek`,
  `collectiveAgreement`), и случайно выбираем среди `HERO_POOL_SIZE` (5) самых свежих подходящих.
- Случайно на каждом рендере, не детерминированная ротация по дате: `/[locale]` и так рендерится
  динамически (`HomePage` принимает `searchParams`), статического кеша здесь рвать нечего —
  подтверждено сборкой (`ƒ /[locale]` в выводе `next build`).
- Карточка в героя — **тот же `<VacancyCard>`**, что и в `/#jobs`, без отдельной вёрстки: вид
  совпадает 1:1 автоматически, включая честное «нужно уточнить» на пустых полях
  (`conditionLine()` в `VacancyCard.tsx` — уже существовало, ничего нового добавлять не пришлось).
- Fallback: если подходящей вакансии не нашлось (`getHeroVacancy` вернул `null`), герой
  рендерится без карточки — только текст и CTA, сетка героя переключается с двух колонок на одну
  (`heroVacancy ? "md:grid-cols-[1.25fr_0.75fr]" : ""`).
- Без Supabase (`isSupabaseConfigured() === false`, локальная разработка без env) — тот же отбор

**Важная находка при проверке на живых данных (16.08.2026, не баг, для понимания поведения в
проде):** на момент написания все 69 published-вакансий в базе — `SOURCE_CONFIRMED`, у всех

(`hours_per_week`, и только для Швеции — у NAV часов в фиде нет, см. `nav.ts`): зарплата, жильё,

первой вакансии, вручную обогащённой редакцией минимум до 3 из 5 полей. Это не ошибка отбора —
пустой герой сейчас честнее, чем демо-карточка, но не путать с «фича сломана»: карточка появится
сама, как только появится хотя бы одна вручную проверенная вакансия.

Формат колонок, правило про `verification_level` (перенос факта из текста объявления НЕ поднимает уровень — это отдельное согласованное правило, не моя догадка), ловушки при чтении шведского текста (`boende` = дом престарелых, не жильё работника, и другие — пойманы вживую при проверке ниже).

## Углублённая проверка перед решением (16.08.2026, три пункта, импортёр по-прежнему не тронут)

### 1. Языковой признак `must_have.languages` — нельзя показывать пользователю ни как есть, ни с
лёгкой оговоркой

Первая гипотеза («кадровые агентства = интернациональные проекты = язык не нужен») проверена и
**опровергнута** для общей популяции: 20 объявлений с пустым `must_have.languages` от компаний с
«bemanning/rekrytering» в названии — 9 из 20 (45%, после вычета одного ложного срабатывания —
«svenska ELLER engelska» матчилось как требование шведского, хотя это выбор языка, не
требование) реально требуют шведский в прозе. Против 4 из 20 (20%, тоже минус одно ложное
срабатывание) у остальных, включая коммуны. То есть просто «это кадровое агентство» не значит
«для интернационального проекта» — большинство кадровых агентств в Швеции обслуживают локальных
клиентов и хотят шведоговорящий персонал не меньше самих клиентов.

Уточнение по свидетельству с реального дата-центрового объекта под Боденом (принято, оно и правда
многое объясняет): переопределил группу (а) по **географии**, не по названию компании — реальные
20 объявлений из Norrbottens/Västerbottens län в общей выборке 225. Здесь пустых
`must_have.languages` уже 18 из 20 (90%) — ближе к свидетельству. Но выборка маленькая, и нашёлся
прямой контрпример, который перевешивает статистику: у **N Kraft Bemanning AB** два почти
идентичных объявления «Grävmaskinister till Luleå & Boden» (id `31356468` и `31356478`) — у
первого `must_have.languages` пустое, у второго — `["Svenska"]`. При этом у **второго** (с
формальным требованием) в самом тексте объявления слово «svenska» не встречается **ни разу**.
Один и тот же работодатель, практически одна и та же вакансия, поле противоречит само себе и не
коррелирует с текстом.

ID06 — проверено на всех ~60 прочитанных вживую объявлениях (40 из стратифицированной выборки +
20 по региону): **0 упоминаний**. Это прямое подтверждение опасения из задачи: требования доступа
на площадку (ID06, инструктаж, сертификаты) живут не в тексте объявления вообще, их нельзя
поймать текстовым поиском ни в каком виде. «Английский как рабочий язык объекта» явно в тексте —
тоже 0 упоминаний на этой же выборке. Когда шведский всё же требуется в прозе — обычно с прямой
причиной («då säkerhetsinstruktioner och arbetsmoment hanteras på svenska» — инструкции по
безопасности на шведском), то есть это не формальность, а реальное ограничение там, где оно есть.

**Вывод: показывать «шведский не требуется» нельзя ни как есть, ни с оговоркой.** Признак ломается
в обе стороны на реальных данных одного и того же работодателя (пусто ≠ действительно не нужен;
и подтверждённое отсутствие в тексте ≠ действительно нет барьера, раз ID06/доступ на площадку в
тексте не фигурируют вообще). Надёжного текстового прокси не нашлось — ID06 не работает, «English
work language» не работает. Остаётся редакционным решением по конкретной вакансии, не
автоматическим фильтром на импорте или отображении.

### 2. Названный vs неназванный коллективный договор — реальное разделение и предложение по схеме

Из 70 объявлений с упоминанием `kollektivavtal` (та же выборка 225) — **13 с явно названным
договором (18.6%), 57 без названия, только общая формулировка (81.4%)**. Одно ложное срабатывание
уже отсеяно вручную («stål» матчилось на «stål- och metallhantering» — отрасль клиента, не
«Stålavtalet»). Из 13 «названных» бóльшая часть на деле называет **сразу несколько** профсоюзов-
контрагентов кадрового агентства («kollektivavtal med Byggnads, Seko, Unionen, Sveriges Ingenjörer
och Ledarna»), а не один однозначный тариф для конкретной профессии — то есть даже «названо» не
всегда значит «можно сразу привязать к ставке», разница с неоднозначностью шведских `members_only`
договоров, уже задокументированной в `resolveAgreements.ts` (`hasAmbiguousSeAgreement`).

Это разные вещи, и текущая схема их не различает: `collective_agreement` (свободный текст) может
содержать что угодно от точного названия до пустой формулировки «есть договор», а на карточке обе
формы рендерятся одинаково — `§ {v.collectiveAgreement}` без разницы в весе.

**Предложение по схеме (не реализовано, только предложение):** триста́йт-колонка по образцу уже
существующих `housing_status`/`travel_status` — например `agreement_status:
'named' | 'exists_unnamed' | 'unknown'`, и `collective_agreement` (текст) заполняется **только**
когда `agreement_status = 'named'`. На карточке:
- `named` — текущая строка `§ {название}`, подразумевает конкретный факт, ничего не меняется;
- `exists_unnamed` — отдельная, визуально более осторожная строка (по духу как жёлтое
  предупреждение `unconfirmedWarning`, не как уверенный факт) — например «Есть коллективный
  договор, название не указано» — чтобы это не читалось как подтверждённые условия;
- `unknown` — как сейчас, ничего не показывается ИЛИ явно «неизвестно», по аналогии с housing/
  travel.

Это тот же паттерн, что уже есть в схеме (`ConditionStatus`), не новая абстракция — переиспользует
уже принятое решение, а не изобретает своё.

## Решение реализовано: OCCUPATIONS + agreement_status (16.08.2026)

### Регион — не языковое поле, вот реальный сигнал

Уточнение, которое отменило первоначальный план: признак «не нужен шведский» не в
`must_have.languages` (см. проверку выше — поле противоречит само себе даже у одного
работодателя), а в **географии**. 90% вакансий без требования языка в реальной выборке
Norrbottens/Västerbottens län — это свойство региона: на северных мегапроектах шведоязычных
физически не хватает для найма, приходится брать бригады откуда есть. Дальше по региону можно
фильтровать — это и сделано (`PRIORITY_REGIONS` в `src/lib/contractors.ts`), а по языковому полю
— нельзя, оно не показывается пользователю нигде.

ID06 — 0 упоминаний на ~60 прочитанных вживую объявлениях. Требования доступа на площадку
(ID06, инструктаж, сертификаты) в тексте объявления не живут — текстовым поиском их не поймать
ни при каком regex, гонять его дальше за ID06/«English work language» смысла нет.

`src/lib/occupations.ts`. Убран мёртвый термин (1 вакансия на регион по всей Швеции), добавлены:

ищут по всей Швеции — их поведение не менялось, сужение коснулось только новых.

`agreementCodeForTerm()` расширен на `term: string | null` — понадобилось для оси по

### Ось по работодателю — `src/lib/contractors.ts`, не внутри `jobtech.ts`

`CONTRACTOR_EMPLOYERS` (N Kraft Bemanning, ExpanderaMera, MW Sverige, MW Field Services, NCC) +
`PRIORITY_REGIONS` (`["25", "24"]` — Norrbotten, Västerbotten). Список работодателей и регион —
конфигурация рядом с `OCCUPATIONS`, не логика импортёра, как и было указано.

**Stegra и Boliden сознательно не в списке** — по находке из проверки выше они публикуют в
основном офисные/управленческие роли, синих воротничков нанимают через таких же подрядчиков, что
уже в списке. Добавление одного из них искало бы не ту популяцию.

**Регион — параметр, не жёсткое исключение навсегда.** `PRIORITY_REGIONS` — обычный экспортируемый
массив кодов län, расширяется добавлением строки, а не правкой логики импортёра. Решение принято
по данным именно северного сегмента (дата-центры/промышленные проекты под Боденом) — когда дойдут
руки до других регионов (Стокгольм, Гётеборг), его нужно пересмотреть, а не считать окончательным.

`src/lib/importers/jobtech.ts`: `fetchJobTechVacancies()` теперь два прохода с **общим** `Set`
дедупликации — сначала по `OCCUPATIONS` (регион только у `regionRestricted` терминов), затем по
`CONTRACTOR_EMPLOYERS` (регион всегда, через новый `employer=` параметр JobTech Search,
подтверждён вживую 16.08.2026). Общий `seen` не просто для эффективности: если бы одна и та же
вакансия (например, `grävmaskinist` от N Kraft — совпадает и по термину, и по работодателю) попала
в оба прохода независимо, один `upsert()` получил бы два объекта с одинаковым
`(source_name, external_id)` — Postgres на multi-row `ON CONFLICT DO UPDATE` в этом случае падает
(«cannot affect row a second time»), а не молча дедуплицирует. `vacancies_source_uq` (миграция
004) остаётся защитой на уровне БД для случая, если термин- и employer-проходы когда-нибудь
разъедутся на два отдельных запроса — но именно упомянутую multi-row-ошибку она не ловит, ловит
только предотвращённый ею дубль строки при раздельных запросах.

Вакансии, найденные по работодателю без совпадения с термином (реальный случай — «Helpers»,
«Dumperchaufförer» у N Kraft), получают `occupation_term: null`, не отбрасываются: карточка и так
умеет показывать такую вакансию (заголовок как есть, без перевода профессии) — отбрасывать их
значило бы вернуться к тому пробелу, ради которого ось по работодателю и добавлена.

### `agreement_status` — тристейт вокруг `collective_agreement`

Миграция `015_agreement_status.sql`. `agreement_status: 'named' | 'exists_unnamed' | 'unknown'`,
тот же паттерн, что `housing_status`/`travel_status` — обычный `text`, не отдельный enum-тип,
валидация на уровне приложения (`toAgreementStatus()` в `src/lib/vacancies.ts`).

Три решения, принятые явно:

1. **`exists_unnamed` засчитывается в порог героя 3/5.** «Lön enligt kollektivavtal» без названия
   — реальная информация (минимум чем-то гарантирован), не пустышка. `HERO_FIELD_TESTS` в
   `vacancies.ts`: пятое условие — `v.agreementStatus !== "unknown"`, засчитывает и `named`, и
   `exists_unnamed`.
2. **`named` и `exists_unnamed` визуально различны на карточке**, не только текстом.
   `VacancyCard.tsx`: `named` — прежняя строка `§ {название}` в общей строке с
   housing/travel/hours (уверенный факт). `exists_unnamed` — отдельная приглушённая рамка (тот же
   визуальный регистр, что у `showAmbiguousSeNote`), формулировка «Коллективный договор есть,
   название не указано» (ключ `vacancy.agreementExistsUnnamed`, во всех пяти словарях) — не
   «условия соответствуют договору».
3. **Расчёт/показ тарифной ставки работает только при `agreement_status = 'named'`** — правило,
   которое должно пережить будущие правки тарифной части, поэтому оно не только в коде, но и в
   схеме:
   - `toAgreementRate()` в `vacancies.ts` — первая строка функции: `if (row.agreement_status !==
     "named") return null;`, до любого обращения к `collective_agreements`/`collective_agreement_rates`.
   - CHECK-констрейнты в БД (`vacancies_agreement_name_ck`, `vacancies_agreement_rate_ck`):
     ни `collective_agreement` (текст), ни `collective_agreement_id` (FK на ставку) физически не
     могут быть заполнены, если `agreement_status` не `'named'` — даже будущий баг в коде
     импортёра или редакционная правка через Studio мимо этого правила не пройдут на уровне базы,
     не только на уровне рендера.
   - Оба импортёра (`/api/import`, `/api/import-nav`) ставят `agreement_status: "named"` в одном
     объекте с `collective_agreement_id`, когда матч найден (норвежский `universally_binding`
     путь) — и НЕ трогают поле, если матча нет, чтобы `upsert` не затирал возможную ручную правку
     редакции при повторном импорте той же вакансии.
   - На сегодня (16.08.2026) в `collective_agreements` только один договор (PAN 25, `members_only`
     — не подходит под автоматическую привязку), поэтому автоматический NO-путь пока не
     активируется ни для одной вакансии на практике: правило уже готово к моменту, когда появится
     первый `universally_binding` договор, но сейчас `agreement_status = 'named'` может выставить
     только редакция вручную через Studio (документировано в `docs/manual-enrichment.md`).

Побочно поймана и починена настоящая уже существовавшая проблема в файле при этой правке:
JSDoc-комментарий `getVacancies()` был осиротевшим — стоял над `HERO_FIELD_TESTS`/
`getHeroVacancy()` вместо самой функции (сдвинулся при более ранней вставке героя в этот же день).
Перемещён на место, логика не менялась.

## Ядро бренда — не ломать
`verification_level` и `publication_type` — **две независимые колонки**.
- `verification_level` меняет только редакция (сервисной ролью).
- `publication_type` меняет оплата.
- Серверный роут оплаты не должен касаться `verification_level` вообще. Пути «купить плашку» не существует ни в данных, ни в коде.
- Порядок выдачи в `getVacancies()` не зависит от `publication_type`.
- Условия показываем всегда, включая `deducted` («жильё вычитается из зарплаты») — это красный флаг для работника.
- Демо-карточки помечаются `is_demo` и подписью «Демонстрация»: пример нельзя выдавать за проверенную вакансию.
- `sourceUrl` — только ссылка на конкретное объявление, никогда на общую страницу поиска биржи
  труда: сосед-тестировщик 14.08.2026 нажал «Оригинал» и попал в тупик на шведском. Нет реальной
  ссылки на конкретный листинг — значит `sourceUrl: null`, а не приблизительная ссылка «похоже на то».
- `VacancyCard` предупреждает про язык оригинала перед переходом (SOURCE_LANGUAGE) — это не
  перевод и не сообщение за работника, просто подготовка человека к тому, что он увидит.
- У каждой опубликованной вакансии должна быть дата последней проверки источника. Закрытая или
  недоступная ссылка не остаётся в выдаче как актуальная: её скрывают или явно помечают.
  **НЕ РЕАЛИЗОВАНО** (записано 14.08.2026 как решение, код не проверяет `application_deadline`
  и не убирает истёкшие/недоступные ссылки) — либо построить, либо убрать пункт, чтобы файл не
  расходился с реальным поведением сайта.
- Зарплата всегда показывается с единицей (брутто/нетто и час/месяц), а неизвестное условие
  остаётся `unknown`: нельзя дополнять карточку предположениями.

## Email-уведомления о новых вакансиях (14.08.2026)
Бесплатно, без аккаунтов и паролей — email + фильтр (профессия/страна, как в поиске), двойное
подтверждение по GDPR, отписка в один клик по токену в каждом письме. Сознательное решение
(запрос "10 € за уведомления" от тестировщика) — см. память проекта: это ретеншн-механика, не
платная услуга, монетизировать её сейчас значило бы душить аудиторию, которая потом делает
осмысленной продажу охвата работодателям.

- `job_alerts` — новая таблица (`006_job_alerts.sql`). anon может только INSERT (форма подписки);
  SELECT/UPDATE — только `service_role`. Дубликат email+фильтра ловится по коду ошибки `23505`
  (unique constraint), отдельный SELECT для проверки "уже подписан" анону не нужен и не дан.
- `subscribeToAlerts` (Server Action) — валидирует email, генерирует `confirm_token` и
  `unsubscribe_token`, пишет строку, шлёт письмо-подтверждение через Resend.
- `GET /api/alerts/confirm?token=` и `GET /api/alerts/unsubscribe?token=` — находят строку по
  токену через service_role, проставляют `confirmed_at`/`unsubscribed_at`, редиректят на
  `/alerts/status`. Без токена или с неверным — состояние `error`.
- `GET /api/notify` — та же авторизация, что у `/api/import` (`IMPORT_SECRET`/`CRON_SECRET`, один
  набор секретов на оба cron-роута). Для каждого подтверждённого неотписавшегося подписчика ищет
  вакансии с `created_at >` его `last_notified_at` (или `confirmed_at`, если писем ещё не было) —
  **не** `updated_at`: апсерт импортёра трогает `updated_at` у ВСЕХ вакансий при каждом ре-импорте,
  включая уже виденные, `created_at` меняется только один раз при первой вставке строки. Если
  письмо не отправилось — `last_notified_at` не двигаем, попробуем в следующий прогон.
- Расписание в `vercel.json`: `/api/import` в 05:15 UTC, `/api/notify` в 05:30 — 15 минут запаса,
  чтобы к моменту рассылки свежие вакансии уже были в базе. Hobby-план: до 2 cron-задач, не чаще
  раза в день каждая — ровно на пределе.
- `src/lib/email.ts` — отправка через Resend (`RESEND_API_KEY`). Домен ещё не верифицирован —
  письма идут с общего тестового адреса `onboarding@resend.dev`. **Важное ограничение Resend,
  не баг**: с этого адреса можно слать только на email самого владельца аккаунта Resend
  (`toliashvili@gmail.com`), на любой другой адрес — 403 `validation_error`. Пока нет
  верифицированного домена, реальные подписчики с других email не получат писем вообще — это
  блокер для публичного запуска, не только для тестов. Когда появится домен `.lv` — верифицировать
  в Resend и задать `ALERTS_FROM_EMAIL`.
- `NEXT_PUBLIC_SITE_URL` — абсолютный адрес для ссылок в письмах (подтверждение/отписка не могут
  быть относительными). Локально `http://localhost:3000`, на проде — адрес деплоя.

**Проверено end-to-end вручную 14.08.2026** (локально, реальные письма через Gmail): подписка →
